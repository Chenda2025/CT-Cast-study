Case Study 2

Balancing Compression Trade-Offs

For high-speed data processing on a single machine

Use ← → arrow keys or the buttons below

Core idea

Compression saves space but costs CPU time.

Compression helps

Smaller files mean less disk I/O and a smaller memory footprint.

Compression costs

The CPU must decompress every block before the data can be used.

Goal: find the balance point where I/O savings beat decode cost.

Two competing bottlenecks

CPU bottleneck

Too much decoding work — the processor cannot keep up.

Disk I/O bottleneck

Reading large uncompressed files is slow.

Step 1

Download the dataset

Fetch a compressed dataset from a public online repository.

def download_dataset(url, dest):
    with httpx.stream("GET", url, follow_redirects=True) as r:
        with open(dest, "wb") as f:
            for chunk in r.iter_bytes(64 * 1024):
                f.write(chunk)

If the network fails, a synthetic dataset is generated so the demo still runs.

Recommendation

On this machine, LZ4 on Parquet gave the best wall-clock time (about 8× faster than uncompressed CSV), because decoding is cheap and the files are already small enough that heavier compression does not pay off.

When storage is slow or data is much larger, Zstd levels 3–9 usually win instead.

Bcolz is old — use the modern stack

Legacy

Bcolz — no longer actively maintained

Modern replacements

  • Parquet — columnar analytics standard
  • Arrow / Feather — very fast in memory
  • Blosc2 — multi-threaded decompression
  • Zarr — chunked N-dimensional arrays

Why theory says this happens

Amdahl's Law

Once disk time shrinks, the remaining decode work dominates total time — so more compression stops helping.

Roofline model

Performance is capped by bandwidth or by compute. The best codec sits on the ridge between the two.

Multi-threaded decompression (Blosc2, Zstd) pushes the CPU limit higher by using more cores.
